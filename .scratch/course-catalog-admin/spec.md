# Add-course button on the course catalog page

Status: needs-info

## Problem Statement

The owner sent a screenshot of `https://varasarn-close-friend.vercel.app/` (a signed-in admin session) showing a "+ เพิ่มรายวิชาใหม่" (add new course) button next to the "รายวิชาทั้งหมด" heading on the course catalog page, opening a small modal with three fields (รหัสวิชา, ชื่อวิชา, หมวดหมู่) and a save button. This rebuild's catalog page has no such button — creating a course is only reachable through the separate "แดชบอร์ดผู้ดูแล" (admin dashboard) screen, in a larger inline form mixed with categories, offerings, bulk import, proposals, and moderation.

## Which site is `varasarn-close-friend.vercel.app`?

Worth flagging: an earlier entry in `.scratch/review-to-timetable/spec.md` (2026-09-24, "Removed the ข้อมูลจากรีวิว line...") stated this URL is "an older deployment of this same rebuild, not the pre-rebuild legacy HTML." That was not verified at the time and this session found evidence against it: the exact string "เพิ่มรายวิชาใหม่" and this modal's markup exist in `git show 0b1b1c8^:index.html` (the true legacy interface per `docs/original-ui-reference.md`) but appear nowhere in this repo's history — not in `src/App.vue` (`git log -S` across all branches finds no commit), and not in `old-repo/index.html` either (the "later Vite entry page, not the original interface" the docs also mention). The simplest explanation consistent with all the evidence is that `varasarn-close-friend.vercel.app` is the actual pre-existing production site (likely serving something at or near the true legacy interface) that this rebuild is meant to eventually replace via Ticket 16's cutover — a separate deployment/codebase, not a past commit of this repo. This still isn't independently confirmed (the page is behind Google sign-in, which this session cannot do), so treat it as a strong inference, not a fact, and correct both spec entries if it turns out wrong.

## Solution

Add the same button and modal to this rebuild's catalog page, backed by the admin dashboard's existing `createCourse` RPC path, gated to accounts with an admin/owner role (consistent with how the dashboard link itself is gated) rather than shown unconditionally — this rebuild has a real role system the legacy trust-based site didn't, and the create-course RPC is admin-only server-side regardless of what the button shows.

## Implementation Decisions

- Reuse `adminService.createCourse` / the existing `courseCode` / `courseName` / `courseCategoryId` / `categories` state rather than introducing a parallel form. Extracted the shared save logic from `addCourse()` (used by the dashboard's inline form) into `saveCourse()`, so the new catalog-page path (`openCourseModal()` / `submitCourseModal()`) doesn't inherit `addCourse()`'s post-save `openDashboard()` navigation, which would be wrong when triggered from the catalog page.
- Reused the existing `.contact-panel` / `.contact-modal-card` / `.contact-modal-header` overlay classes (already used for the "ติดต่อผู้ดูแล" panel) for visual consistency instead of introducing a new overlay family; added one new `.course-modal-body` rule (`.contact-modal-body` centers its content, which suits contact buttons but not a form).
- Button visibility: `v-if="accessRole"`, matching the existing `แดชบอร์ดผู้ดูแล` account-menu item's gating. The dashboard's own inline "เพิ่มรายวิชา" form is left as-is (untouched, still works, still mixed in with the rest of the dashboard) — this is an additive quick-access entry point, not a replacement.

## Testing Decisions

- New file `tests/course-catalog-admin.test.ts`: asserts the button is absent for a signed-in reader with no role, and that for an `administrator` role it opens the modal, submitting calls `create_course` with the expected `p_code`/`p_name_th`/`p_category_id` args, and the modal closes afterward.

### 2026-09-24 — Owner report: course "didn't appear", no confirmation either way; root cause was an unreadable duplicate-code error

The owner reported that a course added through this modal didn't show up in the catalog, and that there was no toast/confirmation either way. Investigating found two separate, real gaps, not one bug:

1. **No success feedback existed at all.** Unlike the timetable's add flow (`showToast()`), neither `submitCourseModal()` (this catalog-page modal) nor `addCourse()` (the admin dashboard's own inline form, which shares the same `saveCourse()`) ever called `showToast()`. So even a fully successful save gave no positive confirmation — easy to mistake for "nothing happened."
2. **`courses.code` already has a `UNIQUE` constraint** (`courses_code_unique`, from the very first migration). A duplicate code was never silently accepted — the RPC was already rejecting it — but the only error surfaced was the raw Postgres text (`duplicate key value violates unique constraint "courses_code_unique"`), shown in the modal's `.alert-danger`. That reads like a crash, not "this code already exists," and the modal correctly stayed open with nothing added — which is almost certainly what the owner hit: a course code that already existed, with an error message that didn't read as an error.

No evidence of a third, separate "creation actually succeeds but catalog doesn't refresh" bug — `submitCourseModal()` already calls `loadCatalog()` after a successful save, and `categories.value` is populated at app mount for every signed-in user (`onMounted`, not gated on visiting the dashboard first), so the category dropdown isn't empty on a fresh catalog-page visit either.

**Fixes:**
- Migration [`db/drizzle/0035_course_duplicate_code_error.sql`](../../db/drizzle/0035_course_duplicate_code_error.sql): `api.create_course()` now pre-checks `EXISTS(SELECT 1 FROM courses WHERE code = v_code)` and raises `รหัสวิชา % มีอยู่แล้ว` (this course code already exists) before attempting the insert — same style as the function's existing "category not found" check, not a new exception-handling pattern for this codebase. Same normalization (`upper(regexp_replace(...))`) as before, so the check and the constraint it's guarding against always agree.
- [`src/App.vue`](../../src/App.vue): both `submitCourseModal()` and `addCourse()` now call `showToast()` on success — "เพิ่มรายวิชาสำเร็จ" for a create, "บันทึกรายวิชาสำเร็จ" for an edit via the dashboard form (captured `wasEditing` before `saveCourse()` resets `editingCourseId`).

New tests in [`tests/course-catalog-admin.test.ts`](../../tests/course-catalog-admin.test.ts): the existing create-course test now also asserts the toast text; a new test submits a code that's already in the mocked catalog and asserts a friendly Thai message appears in `.alert-danger`, the modal stays open, and no toast fires. `npm test` (78/78, +1 new) and `npm run build` passed. Applied the migration to the production Neon branch (owner confirmed first) using `.env.local`'s existing credentials, sourced into a subshell and never printed; verified directly against the database via `pg_get_functiondef` that the duplicate-check text is present in the live function. Live signed-in browser acceptance remains open.

### 2026-09-24 — Real bug found: the Data API paginates, and nothing in this app ever asked for more than the default page

The owner reported the added course (and "the older newly added ones too") still weren't showing in the catalog, even after a hard refresh. The previous entry's "stale browser page" conclusion was wrong — retracted here. The owner pasted the actual `list_approved_catalog` response their browser received: **exactly 100 rows**, alphabetically cut off mid-list at `JC327`.

Root cause: `api.list_approved_catalog()` has 214 rows in production (verified directly against the database — `TEST`, `TEST1`, `TEST3`, `TEST4`, `TEST5` all present, `status='approved'`, correctly joined to their category), but the Neon Data API paginates `RETURNS TABLE` results and defaults to the first 100 rows unless the caller explicitly requests a wider range via `limit`/`offset` query params (`.range()` in `@supabase/postgrest-js`, which the Data API client is built on). Nothing in this codebase's `loadCatalog()` (or the admin dashboard's `listManageableCourses()`, which queries the same `courses` table and is almost certainly hit by the identical cutoff) ever requested a range, so every course past row 100 (alphabetically, by `code`) has been silently invisible in both the public catalog and the admin dashboard since the catalog grew past 100 entries — not something this session introduced.

Ruled out before landing on this: the database itself (direct SQL confirms all 214 rows including the new ones, correctly `status='approved'`), the deployment being stale (asset hash of the live site matched a fresh local build of current `HEAD`), RLS (`courses`/`categories` have `relrowsecurity=true` but zero policies and `relforcerowsecurity=false`, so the `SECURITY DEFINER` function's owner-level execution isn't blocked by it), and browser HTTP caching (the RPC call is POST by default, not GET, so not cacheable).

**Fix:** added `withRange()` to [`src/neon.ts`](../../src/neon.ts) — calls `.range(0, to)` on the query builder when that method exists (the real `@supabase/postgrest-js` builder), and passes the query through unchanged otherwise (every test file mocks `neon.rpc` as a plain async function returning a resolved `{data,error}` object, which has no `.range` method — this keeps all of them working without touching their mock shape). Applied it to the two call sites proven or near-certain to exceed 100 rows: `loadCatalog()` in [`src/App.vue`](../../src/App.vue) and `listManageableCourses()` in [`src/services/admin.ts`](../../src/services/admin.ts), both requesting up to 5000 rows. Did **not** apply it blanket to every RPC call in the app (e.g. per-course offering lists, per-user timetables, category lists) — those are all bounded by something small (one course's offerings, one user's selections, the category count) and are not known to be anywhere near 100 rows; adding it everywhere speculatively isn't warranted by evidence. Flagging as a pattern to watch: any future `RETURNS TABLE` RPC whose result could plausibly exceed 100 rows needs the same treatment.

Every test file mocking `../src/neon` needed a `withRange: (query) => query` addition to its mock object, since `vi.mock` fully replaces the module and the real file now exports it too — without this, `App.vue`'s `import { withRange } from './neon'` resolves to `undefined`, breaking on first call. Added a new [`tests/neon.test.ts`](../../tests/neon.test.ts) unit-testing `withRange` directly: calls `.range(0, to)` when available, passes the query through unchanged otherwise. `npm test` (80/80, +2 new) and `npm run build` passed. Could not verify this end-to-end against the live Data API (would need a signed-in browser session to get a JWT) — the mechanism is standard PostgREST-style pagination override, but if the Data API turns out to enforce a *hard* max lower than the requested 5000, this needs follow-up (e.g. looping pages) rather than a single wider request. Live signed-in browser acceptance — specifically confirming `TEST5` (or any course past the old row-100 cutoff) now appears in both the catalog and the admin dashboard — remains open.
