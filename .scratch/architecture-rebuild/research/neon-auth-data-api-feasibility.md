# Neon Auth, browser data access, and free-hosting feasibility

Retrieved: **2026-09-23**. Scope: [architecture spec](../spec.md) and [ticket 01](../issues/01-authenticated-review-tracer.md). This is documentation research, not a successful deployment or security test. No services were provisioned and no credentials were used. Sources below are current official Neon, Vercel, Google, and PostgreSQL documentation; Neon pages were fetched as live Markdown because the browser fetcher rejected their content type. The existing application has no authentication or backend implementation suitable for reuse in this tracer.

## Decision

**Proceed with a small feasibility tracer, with explicit gates before committing the production architecture.** Browser → Neon Data API → PostgreSQL permissions/RLS and narrowly scoped SQL functions is a documented architecture. A separate application backend is not inherently required for transactional reviews. Vue integration and cross-site authentication behavior remain unproven, however, and the ticket currently overstates signed-out denial and understates the work needed for anonymity. Free idle wake-up is supported; uninterrupted operation within free quotas is not guaranteed. See the evidence and gates below.

## Verified product capabilities and limitations

### Hosting and Vue authentication

- Vercel documents Vite deployments and SPA deep-link rewrites to `index.html`. A Vue SPA can use this hosting model; its static shell and assets remain downloadable without an application session. **Inference:** protected content must be fetched after authentication, with no private data embedded in built assets. Literal HTTP denial of every page requires an additional server-side gate, and login/callback routes must remain reachable. [Vercel Vite documentation](https://vercel.com/docs/frameworks/frontend/vite)
- Neon now calls its service **Managed Better Auth**, marks it generally available, and lists Next.js and React-based frameworks as supported. Vue is absent from that support table. Its SDK separately documents a default Promise-based `BetterAuthVanillaAdapter`, which makes custom Vue integration plausible but is not evidence that this exact integration has passed browser testing. Pin the SDK version and build a small Vue session wrapper. The single-URL `createClient(url)` syntax requires `@neondatabase/neon-js` 0.7.0-beta or later; the object form supports separate Auth and Data API URLs. [Neon roadmap](https://neon.com/docs/auth/roadmap), [SDK reference](https://neon.com/docs/reference/javascript-sdk)
- The service is currently available in AWS regions, not Azure. Users, sessions, and OAuth configuration reside in `neon_auth`; authentication branches with the database. **Design implication:** keep development identities isolated and avoid casually cloning production identity data into previews. [Auth overview](https://neon.com/docs/auth/overview)
- Browser sessions use HTTP-only cookies. The JWT guide explicitly warns about Safari ITP and third-party-cookie limitations in cross-domain setups; `credentials: 'include'` alone does not resolve browser blocking. The roadmap also says separate frontend/backend deployments are not yet supported, while the JWT guide documents token-based calls to separate services. Treat the supported cookie/session layout as a proof gate, not an assumption. A same-origin proxy may be needed; Vue-specific proxy integration was not verified here. [Authentication flow](https://neon.com/docs/auth/authentication-flow), [JWT guide](https://neon.com/docs/auth/guides/plugins/jwt), [roadmap](https://neon.com/docs/auth/roadmap)

### Google-only identity

- Google OAuth works with shared Neon development credentials; production should use an owner-controlled Google OAuth client ID and secret configured in Neon. Google's authorized redirect URI is `{NEON_AUTH_BASE_URL}/callback/google`; the application's `callbackURL` is the later landing page and requires a trusted origin. These are distinct URLs and branch configuration matters. [OAuth setup](https://neon.com/docs/auth/guides/setup-oauth)
- Google-only must be enforced in the service. Neon exposes an email/password `enabled` setting and OAuth-provider removal; Email OTP requires email sign-in to be enabled. Disable email/password, leave other providers removed, and inspect/disable independent alternative plugins such as magic-link and phone sign-in. Hiding UI buttons is insufficient. Verify every alternate entry point directly, including password recovery/account linking. [CLI auth configuration](https://neon.com/docs/cli/neon-auth), [Email OTP prerequisites](https://neon.com/docs/auth/guides/plugins/email-otp), [Auth management API](https://neon.com/docs/auth/guides/manage-auth-api)
- The application's identity key should be **Neon Auth `user.id`, carried in the validated Neon JWT `sub`**, obtained server-side as `auth.user_id()` (text). It is not the Google ID token's raw subject and must not come from form data. Google independently documents that its email claim can change and says “Always use the `sub` field.” Keep the Google-provider mapping inside managed auth; do not invent an email-based merge. [Neon authentication flow](https://neon.com/docs/auth/authentication-flow), [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect)
- “Verified Google account” proves successful Google authentication; it does not establish student enrollment or one human per account. Google also says it is not authoritative for ownership of third-party email addresses without Gmail/Workspace indicators. The spec correctly defers university verification. [Google ID token verification](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)
- Neon’s OAuth guide overgeneralizes Testing-mode restrictions. Google's own documentation gives basic identity-only scopes (`openid`, email, profile) an exception to the test-user allowlist and seven-day authorization expiry. Do not assume a 100-user launch blocker for pure sign-in. Confirm the actual requested scopes and production branding/verification requirements; extra sensitive scopes change the rules. [Google audience settings](https://support.google.com/cloud/answer/15549945?hl=en), [Google OAuth app states](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview)

### Data API and the actual security boundary

- The Data API explicitly supports browser HTTP access, validates JWTs, respects PostgreSQL RLS, and implements PostgREST-compatible queries. The SDK forwards tokens and supports `.rpc()` calls to database functions. Only publish the credential-free HTTPS endpoint; never publish a PostgreSQL connection string, migration credential, OAuth secret, or Neon management API key in `VITE_*`. [Data API overview](https://neon.com/docs/data-api/overview), [getting started](https://neon.com/docs/data-api/get-started), [SDK](https://neon.com/docs/reference/javascript-sdk)
- PostgreSQL grants and RLS are separate controls. Neon’s default public-schema setup grants authenticated users CRUD on existing **and future** public tables. For this app, skip those blanket grants; inspect and revoke any already installed defaults. Otherwise new audit or identity tables could become exposed accidentally. [Data API access control](https://neon.com/docs/data-api/access-control), [setup grants](https://neon.com/docs/data-api/get-started)
- Exposed schemas are configurable and default to `public`; choose only a dedicated `api` schema. Keep internal tables and `neon_auth` unexposed and ungranted to ordinary callers. Set response-size limits and production CORS origins, but test authorization without relying on CORS. Note that updating Data API settings via PATCH replaces the entire settings object and schema changes require a cache refresh. [Data API management](https://neon.com/docs/data-api/manage)
- **RLS controls rows, not author-column secrecy.** A policy permitting everyone to read visible review rows also exposes every granted column in those rows. PostgreSQL owners and `BYPASSRLS` roles can bypass RLS; use application roles without those powers. The authenticated frontend must not receive an owner connection. [PostgreSQL row security](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)
- Ordinary views use the owner's permissions/RLS; `security_invoker` views use caller permissions and need underlying relation access. A view is not automatically an anonymity boundary, and some views are writable. A carefully permissioned projection can work, but a fixed-output RPC with no base-table grants is easier to audit for this first slice. [PostgreSQL views](https://www.postgresql.org/docs/current/sql-createview.html)
- Harden every `SECURITY DEFINER` function: dedicated minimally privileged owner; qualified object names; fixed trusted `search_path` with `pg_temp` last; explicit caller checks; revoke default `PUBLIC` execution and grant only required functions in the same transaction. Do not return an internal review composite type containing identity. [PostgreSQL safe definer functions](https://www.postgresql.org/docs/current/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY)

### Sessions, administrators, and owner powers

- Neon access JWTs expire after 15 minutes and custom claims are currently unsupported. SDK sign-out clears local session state/tokens and synchronizes tabs. The consulted docs do **not** establish immediate invalidation of previously copied Data API bearer tokens. **Inference:** design for the possible expiry window and test it. If immediate post-sign-out revocation is required, a live session check or revocation mechanism is additional work; signature verification alone does not prove a session is still active. [JWT limitations](https://neon.com/docs/auth/guides/plugins/jwt), [SDK sign-out](https://neon.com/docs/reference/javascript-sdk)
- Neon Auth's built-in Admin plugin can list identities, assign roles, reset passwords, and impersonate users. **Do not grant this role to course/review moderators.** It would violate the private-timetable and owner-only-role-management goals. Keep app administrator membership in a private application table, checked on every privileged operation. Even the app owner need not hold Auth Admin in their browser session. [Neon Admin plugin](https://neon.com/docs/auth/guides/plugins/admin)
- **Design inference:** bootstrap one verified Neon user ID as app owner via a controlled migration. App owner grants/revokes app administrators through audited SQL operations; app administrators cannot grant roles, edit review content, or read another user's timetable. Read the membership table each time so revocation is not delayed by a cached role claim. Coordinate role revocation with in-flight operations if strict immediate revocation is required. Technical database/project owners remain trusted operators with underlying data access; app-layer anonymity cannot hide plaintext from them. This distinction should be explicit in the privacy claim. [PostgreSQL RLS privileges and concurrency](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

## Minimal secure implementation proposal

The following is a **design proposal**, not vendor-provided application code or a tested schema:

1. Use Vue/Vite with the vanilla Neon SDK and a custom Google button; route guards provide login UX. Obtain the session through the SDK and use the same client for the Data API. Store no handcrafted identity/token in localStorage. Clear user-specific query state and rendered data on logout/account change. The cookie compatibility gate comes first.
2. Expose only `api` functions: `list_approved_catalog`, `list_visible_reviews`, `create_review`, and initially just enough ownership functionality to test denied mutation. Return explicit safe columns. Private tables hold reviews, ownership, future revisions, memberships, and audit data. Apply RLS to private user records as defense in depth, with deliberate policies for narrowly scoped function-owner roles. Do not assume RLS protects a definer owned by a table owner.
3. `create_review(offering_id, rating, text)` derives its author exclusively from `auth.user_id()`, rejects anonymous/null identity, checks the offering is approved, and sets moderation/author state internally. The caller supplies no author, status, revision, or audit fields. Serialize approval-state changes with review creation using appropriate row locks, so a concurrent operation cannot bypass the approved-offering rule.
4. Put `NOT NULL`, integer rating bounds, trimmed nonempty text, offering foreign key, and **permanent** `UNIQUE(author_user_id, offering_id)` into database constraints. Withdrawal/republishing reuses the record; a partial unique index covering only active reviews would permit duplicates after withdrawal and contradict the spec. Ownerless imported reviews can use nullable authors with normal null-distinct uniqueness, plus an explicit legacy marker unavailable to frontend writes. PostgreSQL warns against cross-table `CHECK` constraints; approval belongs in the trusted write operation/trigger. [Constraint semantics](https://www.postgresql.org/docs/current/ddl-constraints.html)
5. Future edit/withdraw/moderate/approve/merge functions check permissions and change current state plus append history/audit atomically. Lock or version the review for concurrent edits. An edit must not reset moderation status. An administrator who happens to be an author may edit their own review as an author, but cannot edit others' content. Use one transaction per task-oriented call; do not assemble revision history across separate browser requests.
6. `list_visible_reviews` only returns visible author-active reviews and explicit ID/rating/text/offering/date fields; the ID is a review ID, never a user identifier. `my_reviews` and history calls derive caller ownership internally. Admin moderation output omits author mapping. Prevent alternative exposure through embedded relationships, wildcard selection, RPC return types, error details, and audit rows. Review text can itself contain self-identifying details; the promise is absence of system-supplied author identity, not guaranteed resistance to inference from prose.

A small trusted backend is the fallback if cookie compatibility, active-session revocation, or operational controls require it. Keep it same-origin where possible, verify Neon tokens using the branch’s JWKS plus expected issuer/audience/expiry and allowed algorithm, and retain restricted database roles and transaction functions. Do not treat adding an owner-level connection in a server function as equivalent to RLS protection. This fallback is an implementation change to scope explicitly after the tracer, not an already verified Vue integration. [JWT guide](https://neon.com/docs/auth/guides/plugins/jwt)

## Free-tier operation and launch eligibility

Neon documents automatic scale-to-zero after five idle minutes and automatic wake-up on the next query, typically within a few hundred milliseconds. This satisfies the idle-resume requirement within available resources; it is not an availability SLA. [Scale to zero](https://neon.com/docs/introduction/scale-to-zero)

Current Neon Free allowances include 100 CU-hours/project/month, 0.5 GB storage/project, 5 GB monthly public transfer/project, 10 branches/project, and 60,000 Auth MAU. At 0.25 CU, 100 CU-hours equals 400 active hours; all project computes count. A continuously active 0.25-CU compute for 30 days would use 180 CU-hours (**calculation**), so 200 total users alone cannot prove free fit. Quota exhaustion suspends compute until the next period or upgrade; storage growth operations fail at the cap. Avoid keepalive polling, measure Auth/database activity, paginate, cap text size, and monitor test-branch usage. Free recovery history is six hours with a changes cap, plus one manual snapshot; this does not replace the spec's automated independent export/restore plan. [Neon plans and quota behavior](https://neon.com/docs/introduction/plans)

Vercel Hobby currently includes 100 GB transfer, one million edge requests, and one million function invocations; function compute has its own limits. Most exhausted allowances require waiting up to 30 days. Hobby lacks team collaboration features. [Hobby limits, updated September 14, 2026](https://vercel.com/docs/plans/hobby)

Vercel's fair-use page restricts Hobby to “non-commercial personal use only” and counts payment to create/maintain/host a site, paid development staff, advertising, and sales activity as commercial. Donations alone are not commercial. **Unknown:** whether this student project is personally operated, institutionally operated, monetized, or maintained by paid staff. Its 200-user size does not establish eligibility. Resolve operating facts before launch; if unclear, obtain Vercel's answer or use the already-permitted eligible static host. [Vercel fair use, updated September 14, 2026](https://vercel.com/docs/limits/fair-use-guidelines)

## Proof-of-concept and acceptance gates

These steps are recommended work, **not executed tests**:

1. **Compatibility first:** on an isolated development branch, configure Google-only auth and exact callback/trusted origins. Build the Vue client, deploy a preview, and exercise login, redirect, refresh, multiple tabs, sign-out, browser-back navigation, and expiry/renewal in Chrome, Firefox, Safari, and restrictive-cookie modes. Record whether a proxy is necessary. Inspect alternate provider/password/OTP/magic-link/phone endpoints for denial. Do not enable email login in production just to simplify automation.
2. **Identity verification:** use two real Google test accounts to show that Neon session `user.id`, JWT `sub`, and SQL `auth.user_id()` match, while submitted email/author fields cannot affect ownership. Use Google basic identity scopes only unless additional scope is required and documented. Do not automate a real user's Google password; authenticated test credentials/tokens need a dedicated secure fixture workflow.
3. **Data boundary:** run requests through the real HTTP interface with no token, anonymous token, malformed/expired token, a token from another branch, user A, user B, application administrator, and owner. Assert both returned status/data and unchanged database state. RLS may deny by returning no rows rather than producing an HTTP error, so tests must express the intended denial semantics.
4. **Write invariants:** submit valid review; reject null/fractional/out-of-range rating, whitespace-only text, unapproved/nonexistent offering, author spoofing, moderation spoofing, and two concurrent creates. After withdrawal, another create must not allocate a second record; republish reuses the original. Exercise an approved-state race and transaction rollback.
5. **Anonymity/ownership:** user B reads the safe review output but cannot fetch A's identity/history or mutate A's review. Attack direct table URLs, alternate schema headers, select-star/author-column requests, relationship embedding, bulk updates, upserts, RPC outputs, and errors. Check `neon_auth`, membership, audit, and revision surfaces. Verify application administrators cannot call Auth Admin impersonation or read another timetable.
6. **Session/role revocation:** copy a test bearer token, sign out, and replay it immediately and after expiry. Record the observed validity window and match it to the agreed requirement. Revoke app administrator membership and retry privileged operations with the same token; it must fail. Test ordinary owner/admin account capabilities independently of project/database credentials.
7. **Operations:** refresh schema cache after migration; inspect actual grants, function owners, RLS flags, and exposed schemas. Leave compute idle beyond five minutes, then measure automatic recovery without console intervention. Measure representative egress/compute/storage and branch cleanup. Before cutover, run the export/restore exercise and verify host eligibility. Never intentionally exhaust production quotas to test failure handling.

Open gates are therefore bounded: Vue/browser cookie support, Google-only server enforcement, the required logout revocation semantics, actual free-tier consumption, and Vercel operating-model eligibility. The core database permissions and transaction design are feasible, but no live acceptance criterion is proven by this research alone.
